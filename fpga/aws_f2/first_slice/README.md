# ERG-103 custom F2 DDR first slice

This custom CL connects `first_slice_top` and `f2_memory_bridge` to physical
DDR through the pinned AWS `sh_ddr` controller. OCL/BAR0 controls the store and
DOT128 mailbox. PCIS/BAR4 is the sole DDR loader and readback path. There are no
HBM, scrubber, traffic-generator, PCIM or alternate write masters. ASIC-portable
compute/store RTL stays outside the AWS wrapper.

The custom PCI identity is `1d0f:f010`, subsystem `1d0f:0103`. A new AFI is
required: the Week 0 public adder cannot execute this design. The fixed shell
`clk_main_a0` runs at 250 MHz. Simulation and a successful DCP build alone do
not establish physical execution; record the generated AFI/AGFI, shell identity,
source manifest, routed timing, observed DDR digest and actual result logs.

## Memory and locking contract

The allocation must be 64-byte aligned, contain a whole number of lines, and
fit the lower 16 GiB of DDR. The store limits its logical image to 256 MiB.
Host bursts must be INCR transactions of 1–64 bytes per beat, remain within one
4 KiB page, and fit wholly inside the allocation. Unaligned first beats end at
their aligned transfer boundary; subsequent beats start at aligned boundaries.
Narrow accesses retain their byte lanes, including when the shell presents
AxSIZE=6 with a partial first-beat strobe. Strobes before the initial byte
address are rejected. Engine requests still require 64-byte alignment. Each host beat is translated to one aligned
64-byte DDR transaction; this intentionally favors simple verification over
bandwidth. Host write strobes cannot escape the permitted lanes.

Write authorization is captured at AW acceptance. Closing LOADING denies later
AWs but drains an admitted burst and its response before `loader_idle` becomes
true. Denied bursts consume their declared W beats and complete with SLVERR;
they never produce DDR AW/W. Malformed WLAST/strobes also report failure. A
noncompliant sender that omits declared beats can time out; it cannot reopen
the gate or force transaction-ID reuse.

Host readback and engine line reads arbitrate fairly at transaction boundaries.
The DDR side has one read outstanding. Errors return zero data. Every nonzero DDR RRESP/BRESP, bad DDR ID or
missing expected RLAST fails the backend closed; extra read beats drain through
RLAST. If RLAST never arrives, the host must report timeout and reset/reconfigure
coherently. There is no timeout-based ID reuse. Reloading the AFI is the supported
whole-design reset; the wrapper does not expose an in-band unlock or FLR reset.

A complete canonical image claim requires writing and reading back all
242,357,184 bytes and matching the manifest SHA256. A small fixture validates
the path but cannot stand in for that result. The host must flush write-combined
BAR4 writes and perform a same-device read before BEGIN_VERIFY; `loader_idle`
counts accepted AXI transactions, not CPU write-combining buffers.

## Prepare, simulate and build

Use Ubuntu 24.04 x86_64 with Vivado 2025.2 enabled and the existing
[setup](../README.md) completed. Keep enough build space on a dedicated volume;
check current free space before starting. Source and final reports/DCPs must
remain on durable storage if temporary build files use EC2 instance store.
AWS estimates 30–90 minutes for an example DCP build; this design has no measured
build duration yet. AFI ingestion adds asynchronous service time.

```bash
source /tools/Xilinx/2025.2/Vivado/settings64.sh
python3 fpga/aws_f2/first_slice/prepare.py \
  --hdk /absolute/pinned/aws-fpga \
  --fixture /absolute/model/first-slice/fixture.json \
  --image /absolute/model/native/weights.bin \
  --output /absolute/fresh/erg103-build
bash fpga/aws_f2/first_slice/run.sh \
  /absolute/fresh/erg103-build/cl_bonsai_first_slice sim
bash fpga/aws_f2/first_slice/run.sh \
  /absolute/fresh/erg103-build/cl_bonsai_first_slice build
```

Use the actual Developer AMI settings path if it differs. `prepare.py` verifies
HDK/IP/HLX pins, tracked-source cleanliness and LFS objects. It copies only the
specified RTL and scripts to a fresh CL and records their SHA256 hashes. It does
not copy old example build outputs. `run.sh` verifies those bytes, captures logs
and exit codes, and uses the pinned AWS build driver with `--mode small_shell`.
It rejects timing-violated DCPs even if AWS generated a tarball.

`stage_fixture.py` verifies the entire canonical image hash, then selects three
actual Bonsai Q1_0 blocks: the first, one crossing a line, and one crossing a
4 KiB page. It verifies their bytes and hashes and independently recomputes their
signed-int8 dot oracles. The blocks are relocated to offsets 0, 118 and 4082 in
a 4,160-byte fixture; a separate synthetic mixed ternary block occupies
offset 256. Generated bytes and the SV include stay in the external CL work directory.
`compact_fixture.json` records original/relocated addresses, block hashes,
activations, expected dots, raw FP16 scales, and canonical/compact image hashes.

`test_first_slice.sv` uses the AWS shell BFM and DDR simulation controller to
load and read back every compact-fixture byte, seal the store, and execute the
four jobs. It checks the exact signed sum and raw FP16 scale from DDR. This is
a compact relocated fixture, not a full canonical-image load or model inference.
The native runner separately loads and hashes all 242,357,184 canonical bytes.
No XSIM execution is implied by fixture generation or stub-based elaboration.
`f2_memory_bridge_tb.sv` is the focused, vendor-independent protocol regression:

```bash
verilator --binary --timing --assert --top-module f2_memory_bridge_tb \
  -Wno-TIMESCALEMOD --Mdir /absolute/fresh/bridge-obj \
  hdl/verilog/first_slice/f2_memory_bridge.sv \
  fpga/aws_f2/first_slice/f2_memory_bridge_tb.sv
/absolute/fresh/bridge-obj/Vf2_memory_bridge_tb
```

The AWS synthesis result is `build/checkpoints/*.Developer_CL.tar`. After
reviewing the final timing/DCP/source manifest, upload that tar to an authorized
private S3 input location and use `aws ec2 create-fpga-image` with explicit input
and log locations. Poll `describe-fpga-images` until `available`, then recheck
slot ownership/idle state before loading the returned AGFI. These scripts do not
create or load images, start EC2 instances, or change IAM. Use the existing
[physical preparation](../physical/README.md) for the public SDK build; its
Week 0 validation runner is specific to the public adder and must not load over
this custom CL.

## Physical SDK transport and manifest

Build the transport against the same verified SDK, without installing global
libraries or opening an FPGA:

```bash
bash fpga/aws_f2/first_slice/build_transport.sh \
  /absolute/pinned/aws-fpga /absolute/fresh/erg103-transport
```

The build exports tracked SDK sources at the pin, compiles the SDK, statically
links its management library into `transport`, and records binary/source/library
hashes, compiler version and linked system libraries. No mock or CPU dot
implementation is part of this binary. BAR4 uses write-combined loading and
uncached volatile readback; the SDK does not expose AXI response codes through
MMIO, so return values are explicitly labeled SDK completion. The loader drains
each 64-byte write through a same-BAR4 read to bound queued correctness traffic.
The shell PCIS timeout starts at AxVALID, including backpressure; physical
acceptance must compare timeout/error metrics before and after the run. Software
regression and XSIM cannot prove the actual host PCIe transaction behavior. RTL sticky DDR
faults and complete readback/state checks are required in addition.

After an actual successful DCP build and reviewed AFI submission, retain the S3
upload checksum and `create-fpga-image` receipt linking that exact Developer CL
tarball to its AFI. Save `describe-fpga-images` JSON for the available image, then
bind the reviewed evidence:

```bash
python3 fpga/aws_f2/first_slice/bind_manifest.py \
  --cl /absolute/fresh/erg103-build/cl_bonsai_first_slice \
  --build-result /absolute/fresh/erg103-build/cl_bonsai_first_slice/logs/build-RUN/build-result.json \
  --transport-work /absolute/fresh/erg103-transport \
  --afi-description /absolute/evidence/available-afi.json
```

The helper verifies stored DCP/report hashes, compiled-source equality, binary
build hashes and custom PCI identity. It creates `transport.manifest.json` with
schema 1, backend `aws_f2`, actual AGFI, DCP SHA256, transport SHA256, all required
RTL/wrapper/transport source hashes and compiler version. AFI metadata alone
cannot prove which tarball was submitted: retain and review the upload/submission
receipts as part of the report. Do not invent an AGFI or reuse the public adder.

With the new image already loaded on a reserved idle slot and its store EMPTY,
run the shared full-image suite. Substitute the actual recorded AGFI:

```bash
sudo env FIRST_SLICE_EXPECTED_AGFI="${AGFI}" python3 utils/first_slice/run.py \
  --suite native \
  --fixture /absolute/model/first-slice/fixture.json \
  --image /absolute/model/native/weights.bin \
  --transport /absolute/fresh/erg103-transport/transport \
  --build-manifest /absolute/fresh/erg103-transport/transport.manifest.json \
  --out /absolute/fresh/erg103-native-physical
```

The runner also accepts the adjacent manifest when `--build-manifest` is omitted.
`FIRST_SLICE_SLOT` defaults to 0. The transport verifies the loaded AGFI and PCI
identity before mapping BARs, checks cold state, uses an advisory slot lock,
rechecks identity after bulk transfers, and never loads/clears an AFI itself.
Run the synthetic suite after a separate coordinated image reload; a sealed
store cannot be reopened in place. These are reproduction instructions, not a
claim that a custom AFI has been built, loaded or executed.
